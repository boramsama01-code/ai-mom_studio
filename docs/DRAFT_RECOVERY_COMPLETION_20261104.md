# 감사 후속: 입력 복구·게시 준비·버전 복원 마무리

작성: 2026-11-04 한국 시간. 기준 main/운영 커밋은 `b41c2b14af95a095485a32f4e8506d15a6fccc33`(PR #61)이다. 이 문서는 기능 계약과 검증 경계를 기록한다. 최종 실행 결과와 배포 SHA는 이 변경의 PR/CI 및 운영 `/api/health`에서 확인한다.

## 왜 추가 수정했는가

PR #61에서 정상 이동·저장 실패의 입력 보존, 발행 동시성, 결과 미확정 복구를 수정했다. 원래 감사의 세부 권고를 다시 대조하면 세 가지는 남아 있었다.

| 남은 항목 | 확인된 기존 코드 | 이번 변경 |
| --- | --- | --- |
| 강제 탭 종료 후 미저장 원고 복구 | 원고·캡션은 React state, `beforeunload`는 경고만 제공 | 입력 반영 직후 기기에 임시 보관하고, 다시 열면 내용을 비교해 명시적으로 복원 |
| 승인 전 계정·예약 의도 저장 | publication draft는 캡션만 보관, 목적지·시각은 화면의 state | 캡션·계정·지금/예약·한국 시각을 독립 CAS 버전으로 저장 |
| 수집 원고 과거 버전 복원 | 버전 번호·작성자·시각만 표시 | 실제 원고·카드 문구 비교와 새 revision으로 복원 |

기존 React·Wouter·TanStack Query·Express·PostgreSQL·Render 구조를 유지한다. 새 프레임워크·Redis·유료 인프라는 추가하지 않는다.

## 1. 미저장 입력 복구

`draftRecovery.ts`, `useDraftRecovery.ts`, `RecoveryNotice.tsx`를 공용으로 사용한다. 카드 문구, 자료 기반 초안·붙여넣은 원문, 게시 준비, 직접 제작 원고·캡션·설명, 이미지 대체텍스트, 작업 메모에 연결한다. 이미지 파일·인증 토큰·세션 쿠키·API 키는 복구본에 넣지 않는다. 이미지 순서 편집에는 이미 저장한 이미지 ID와 설명만 보관한다.

- 입력이 React 상태에 반영되면 동기적으로 기기 복구본을 갱신한다. 탭 비활성화·종료 이벤트에서도 확인한다.
- 복구본을 자동으로 서버에 저장하지 않는다. **기기 임시 보관**과 **서버 저장됨**은 다른 상태로 표시한다.
- 같은 콘텐츠를 여러 탭에서 편집할 때 물리 저장 슬롯을 분리한다. 한 탭의 저장·버림이 다른 탭의 미저장 원고를 덮어쓰지 않는다. 재열기하면 여러 복구본 중 확인할 것을 선택할 수 있다.
- 복구본을 작성한 뒤 서버 버전이 달라졌으면 양쪽 내용을 비교하고 확인해야 편집기에 불러올 수 있다. 최종 서버 저장에는 기존 CAS가 적용된다.
- 성공한 저장 또는 명시적 버림은 해당 복구본을 정리한다. 저장 요청 중 추가 입력은 저장 응답으로 덮어쓰지 않는다.
- 복구본은 최대 7일, 한 건 256KB, 전체 1MB·20개로 제한한다. 저장소 차단·용량 초과 시 입력을 유지하고 서버 저장을 안내한다. 보관 중인 다른 원고를 조용히 지우지 않는다.
- `/auth/me`가 인증 세션 ID에서 목적을 구분한 HMAC으로 복구 범위를 발급한다. 이 값은 인증 수단으로 사용하지 않는다. 로그아웃·다른 로그인에서는 이전 복구 범위를 정리하며, 오래된 탭의 재기록을 막는다. 취소된 인증 조회의 늦은 응답은 복구 범위를 다시 활성화하지 못한다.

기기 저장소 삭제·세션 만료·저장 공간 차단·운영체제가 입력 반영 전에 프로세스를 종료한 경우까지 영구 보존을 약속하는 기능은 아니다. 지속 보관과 다른 기기에서의 작업은 서버 저장이 기준이다.

## 2. 게시 준비 저장

공유 계약은 `shared/publicationDraft.ts`에 둔다.

```ts
type PublicationOptions = {
  destinationIds: number[];
  timing: "now" | "later";
  scheduledAtKst: string; // YYYY-MM-DDTHH:mm 또는 작성 중 빈 값
};
```

자료 기반 콘텐츠는 `content_items.publication_draft`에 `{ version, captions, options }`를 저장한다. 직접 제작은 `studio_cards.publication_draft`에 `{ version, options }`를 저장하며, 캡션은 기존 원고 버전의 필드로 유지한다. 서로의 mirror API로 저장 기준을 두 개 만들지 못하도록 차단한다.

사용자는 **게시 준비 저장**으로 선택 계정과 시각을 남긴 뒤 화면을 닫았다가 이어서 작성할 수 있다. 빈 계정·빈 예약 시각·과거 시각도 초안으로 저장할 수 있지만 최종 승인은 별도 검증한다. 초기 조회 전에는 선택을 받지 않는다. 저장한 계정이 없어졌거나 연결되지 않았다고 다른 계정을 자동 선택하지 않는다.

캡션·계정·시각 저장은 원고 revision과 이미지 버전을 올리지 않으며, 전송 요청을 만들지 않는다. 변경 시 시작하지 않은 기존 예약의 승인을 철회한다. 화면에서도 이 영향을 안내하고 실제 전송 상태를 다시 조회한다. 전송 중·미확정·성공한 외부 결과는 PR #61의 기존 규칙대로 보존한다.

최종 승인에서는 서버에 저장한 준비 버전, 목적지, 지금/예약 모드, 한국 시각을 모두 비교한다. 계정 확인이 끝난 뒤 트랜잭션 안에서도 다시 검사한다. 한국 시각은 브라우저나 서버의 로컬 시간대와 관계없이 `+09:00`으로 해석하며 잘못된 날짜의 자동 보정을 허용하지 않는다.

서로 다른 탭의 동시 저장은 한 요청만 성공하고 다른 요청에는 409를 반환한다. 화면은 내 입력과 최신 저장본을 비교하게 한다. 저장 응답 v2가 늦게 도착하더라도 이미 조회한 v3의 충돌 표시나 Query cache를 v2로 되돌리지 않는다.

직접 제작의 미리보기·승인 중에는 관련 부모 편집기를 잠근다. 저장은 최신 form ref와 요청 snapshot을 사용하며, 추가 입력을 오래된 응답으로 덮지 않는다. 최종 승인 API가 수행하는 계정 확인을 클라이언트에서 중복 대기하며 오래된 확인 상태를 사용하는 경로는 제거했다.

## 3. 원고 비교·복원

`SourceRevisionHistory.tsx`는 현재 저장본과 선택한 과거 원고의 사실 정보·근거·카드 디자인·표지·본문 문구를 비교한다. 기본은 변경 항목만 보여 주고 동일 항목도 펼쳐 볼 수 있다. 선택하기 전에는 과거 원고 조회를 요청하지 않는다.

복원 전 미저장 편집기를 기존 DirtyGuard로 처리하고 최신 저장본을 다시 읽는다. 확인 이후 새로 입력한 내용도 다시 보호한다. `POST /channels/:cid/items/:id/revisions/:rid/restore`는 item 행 잠금과 version CAS 안에서 새 operator revision을 만든다. 기존 revision을 수정하거나 현재 revision ID를 과거로 되돌리지 않는다.

| 데이터/상태 | 복원 결과 |
| --- | --- |
| 선택한 과거 원고·카드 문구 | 새 revision으로 현재 원고에 적용 |
| 기존 현재/과거 revision | 기록에 보존 |
| 검토 | 다시 검토 필요 |
| 대기 승인·미시작 예약 | 무효화·취소 |
| 전송 중·미확정·성공 결과 | 기존 증거와 상태 보존 |
| 기존 이미지 | 파일 보존, 새 원고와 버전이 달라 재생성 필요 |
| 원문·연결 자료·캡션·계정·예약 초안 | 현재 저장된 값 유지 |

복원 후 카드 편집기의 문구와 템플릿 선택도 새 원고에 맞춘다. 호환되지 않는 예전 payload는 필요한 사실을 임의로 채워 넣어 복원하지 않고 422와 수동 반영 안내를 제공한다. 복원 HTTP 응답을 받지 못하면 자동 재요청하지 않고 최신 버전 기록을 먼저 확인하게 한다.

## 4. 검증과 배포

### 격리 검증

- 실제 PostgreSQL: `publication-draft-postgres`, `source-revision-restore-api`, `draft-recovery-auth-postgres`와 기존 publication/workspace/studio 회귀를 CI의 PostgreSQL 16에서 직렬 실행한다. 테스트 DB의 `resetDb`는 운영 DB에 적용하지 않는다.
- 동시성: 동시 게시 준비 저장, 계정 확인 중 준비 변경, 복원끼리의 경합, 복원과 편집의 경합을 실제 행 잠금/CAS로 확인한다.
- 컴포넌트: 저장 실패·저장 중 추가 입력·늦은 응답·서버 버전 충돌·복구본 선택·복원 동의·연속 클릭을 확인한다.
- 브라우저: `scripts/content-workspace-regression.mjs`에서 320/393/430/1280px, 두 카드 수정·저장·재열기, 강제 탭 종료 후 문구·캡션 복구, 계정·예약 초안 재열기, 즉시/예약·취소·결과 미확정 복구 경로를 확인한다. 모든 API는 합성 자료이고 외부 요청을 차단한다.

최종 CI는 typecheck, 전체 테스트, production build, WebKit 모바일 레이아웃과 작업 흐름을 실행한다. 실제 Instagram/Telegram 게시, 운영 콘텐츠 삭제, 유료 AI 호출은 이 검증에서 실행하지 않는다. 실물 iPhone의 키보드·메모리 회수와 실제 외부 게시 성공은 별도 확인 영역이다.

### 마이그레이션·롤백

`0014_publication_intents.sql`은 `studio_cards.publication_draft` nullable JSONB 컬럼만 추가한다. 기존 원고·승인·외부 게시 기록을 삭제하거나 일괄 변경하지 않는다.

배포 후 main SHA, Render live 배포 SHA, `/api/health.revision`, DB 연결, 시작 로그, 읽기 전용 목록·발행함을 대조한다. 기기 복구본을 테스트하려고 운영 원고를 입력하거나 실제 게시 버튼을 누르지 않는다.

저장 후 재열기 불일치, 최신 준비 버전과 다른 승인 사용, 미저장 입력 소실, migration/DB 오류가 확인되면 추가 게시를 중지하고 수정 또는 앱 롤백을 판단한다. 컬럼과 시도 기록은 롤백 때 삭제하지 않는다. 이전 앱은 게시 준비 의도 검증을 모르므로 게시를 활성화한 채 되돌리지 않는다. PR #61 이전 앱으로의 롤백은 기존 전송 phase·lease 안전 규칙도 함께 고려해야 한다.

무료 Render의 휴면에 따른 예약 지연, 접근 제한 기사, 외부 API 성공 여부를 자동으로 확정할 수 없는 응답 유실은 이 변경으로 사라진다고 주장하지 않는다. 이전 보고서의 운영 한계와 명시적 결과 확인 절차를 유지한다.
