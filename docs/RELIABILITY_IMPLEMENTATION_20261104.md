## 2. 운영자가 사용하는 흐름

주 메뉴는 **내 콘텐츠 / 수집함 / 발행함**이다. 수집함에서는 원문을 선택하고 초안을 시작한다. AI가 실패해도 직접 초안을 만들 수 있다. 초안부터 내 콘텐츠에 나타나며, 카드 문구·미리보기·게시 캡션·계정 확인은 같은 편집 공간에서 진행한다.

카드 안의 문구는 원고 revision에 저장한다. 인스타그램·텔레그램 게시 캡션은 `content_items.publication_draft`의 독립 버전으로 저장하므로 캡션 저장만으로 이미지를 다시 만들지 않는다. 캡션이 바뀌면 대기 승인은 철회한다. ZIP의 caption.txt도 저장한 캡션을 사용한다.

사용자는 저장됨, 미저장, 저장 오류, 다른 저장본과의 충돌을 구분할 수 있다. 다른 채널 선택은 열린 콘텐츠를 다른 콘텐츠로 바꾸지 않는다. 콘텐츠를 떠날 때 저장 후 이동·버리고 이동·머무르기를 선택한다. 저장에 실패하면 편집기에 남는다.

이미지 버전은 원고 revision과 비교해 오래된 결과임을 표시한다. 캡션·원문·대체텍스트·카드 문구가 저장되기 전에는 기존 승인본으로 바로 발행하지 않는다.

## 3. 게시 상태와 동시성 계약

| 상태 | 허용하는 행동 | 금지하는 행동 |
|---|---|---|
| 초안·검토 전 | 편집, 저장, 미리보기 갱신, 검토 완료 | 실제 게시 승인 |
| 검토 완료·대기 승인 없음 | 계정·캡션 확인 후 즉시 또는 예약 승인 | 오래된 이미지·캡션으로 승인 |
| 예약 대기 | 대기 예약 취소, 편집 후 재검토 | 같은 원고 중복 승인 |
| 준비·전송 중 | 진행 확인, 아직 시작하지 않은 다른 목적지 취소 | 해당 전송 재시도, 다른 버전 새 승인 |
| 성공 | 게시물 보기, 기록 확인 | 성공한 전송 재전송 |
| 확정 실패 | 오류 확인, 승인·계정이 유효할 때 그 목적지만 재전송 | 유효하지 않은 옛 승인 재사용 |
| 결과 미확정 | 외부 결과 재조회, 이미 게시됨 기록, 미게시 확인 | 자동 재전송·새 버전 승인 |
| 미게시 확인 | 최신 유효 승인이면 별도 재전송, 옛 승인이면 종결 후 새 승인 | 확인과 동시에 묵시적 재전송 |
| 일부 완료 | 목적지별 성공·실패·취소·대기를 각각 확인 | 전체 성공 또는 전체 취소로 표시 |
| 취소 | 최신 내용 재검토·새 승인 | 취소한 승인 자동 재개 |

잠금 순서는 콘텐츠 → 관련 전송(정렬) → 승인이다. Studio 수정은 콘텐츠 → Studio 카드 순서로 잠근다. 외부 게시 요청 전 별도 트랜잭션에서 최신 자격·계정·lease를 검사하고 `dispatching`을 기록한다. 이 커밋이 취소와 게시 요청 시작을 구분하는 기준이다. 네트워크 호출을 이 잠금 구간에 넣지 않는다.

`delivery_attempts`와 `delivery_attempt_events`는 추가만 가능한 기록이다. lease를 잃은 작업자가 보낸 늦은 성공 응답도 버리지 않는다. 서로 다른 게시물 ID가 발견되면 결과 확인 대상으로 남긴다. 내부 중복 방지와 외부 API의 결과 증명은 별개다. 응답을 잃었다는 이유만으로 미게시를 단정하지 않는다.

Instagram 컨테이너의 PUBLISHED만 있고 게시물 ID가 없는 경우 자동 성공으로 확정하지 않는다. 실제 게시물 주소 또는 ID를 운영자가 확인한 기록은 `operator_confirmed`로, 외부 성공 응답은 `provider_verified`로 구분한다.

## 4. AI 요청과 원문 보존

소스 초안·카드 문구 요청은 기존 동기 API 응답 형식을 유지하면서 DB jobs에 먼저 기록한다. 같은 requestId의 완료 응답은 재생한다. 실행 중 요청 ID를 다시 보내면 추가 과금 호출을 만들지 않는다. 원고 반영과 replay 응답 저장은 같은 트랜잭션이다. 서버 중단으로 완료 여부를 모르는 유료 요청은 lease 만료 후 실패 기록을 남기며 자동 재실행하지 않는다.

브라우저는 진행 중 요청의 ID와 provider/template/version만 sessionStorage에 보존한다. 직접 입력한 원고나 인증정보를 넣지 않는다. 응답 유실 뒤 재확인에는 원래 요청 ID를 사용한다. 명확하게 종료된 실패 뒤 사용자가 다시 생성을 선택하면 새 요청이다. 취소 요청이 원래 생성 요청보다 먼저 도착해도 DB 취소 기록이 이후 실행을 막는다.

취소 신호는 OpenAI·Claude·Gemini 어댑터에 전달된다. 취소와 저장이 경합하면 DB에 먼저 확정된 상태를 따른다. 이미 시작된 공급자 요청의 과금 취소를 보장하지 않는다. Gemini의 일시적 503·일시 호출 제한에만 제한된 재시도를 하며 인증·일일 한도·과금 제한·응답 미확인 요청을 자동 반복하지 않는다.

원문 fetch는 네트워크 밖에서 수행한 뒤 최신 source 행을 잠그고 저장한다. 실패 이력과 사용 가능한 본문 상태는 구분된다. 수집 시각이 더 오래된 응답이 나중에 도착해도 최신 본문을 덮어쓰지 않는다. 원문 내용이 바뀌면 검토를 다시 요청하고 대기 승인을 철회한다.

## 5. 마이그레이션·기존 데이터·배포

- `0013_publication_recovery.sql`은 기존 행을 삭제하지 않고 캡션 초안, 승인 요청 ID, 목적지 스냅샷, lease·전송 단계, 시도 기록, heartbeat 테이블을 추가한다.
- 기존 승인에는 검증된 계정 스냅샷이 없으므로 자동으로 추정해 채우지 않는다. 해당 대기 전송은 `approval_required`로 중단하고 최신 계정·원고를 다시 승인하도록 안내한다.
- 이전 버전에서 남긴 processing 행은 게시 전이었다고 증명할 수 없으므로 unknown으로 보낸다. 운영자가 실제 계정에서 확인해야 한다.
- 이전 succeeded 행 중 ID가 `undefined/null/NaN/빈 문자열`이거나 ID와 게시물 주소가 모두 없는 기록은 결과 확인 대상으로 바꾼다. 외부로 재전송하지 않고 원래 기록을 시도 이력에 남긴다. 정상 ID와 운영자 확인 기록은 유지한다. 운영에 이런 행이 실제로 있었다는 의미는 아니다.
- 앱 시작 시 기존 초안을 내 콘텐츠와 연결하는 backfill은 advisory lock과 완료 표식을 사용한다. 기존 카드·휴지통·이미지는 보존한다. AI나 게시 API를 호출하지 않는다.
- SIGTERM/SIGINT 시 새 작업을 받지 않고 AI·수집 요청에 중단 신호를 전달한다. 게시 작업에는 결과를 저장할 시간을 주고, 25초 안에 종료한다. 완료하지 못한 작업은 저장한 lease·phase로 판정한다.
- `/api/health`의 revision과 capabilities를 배포 커밋과 대조한다. Render 배포가 live인 것만으로 외부 게시 성공을 주장하지 않는다.

## 6. 검증과 실제 외부 연동의 경계

실제 PostgreSQL 16을 쓰는 CI에서 운영 함수의 별도 연결·행 잠금·트랜잭션으로 취소/claim, 두 워커, 중복 재전송, 요청 ID, 오래된 성공 응답, caption CAS, 원문 재수집 경합을 검증한다. 외부 Instagram·Telegram·Cloudinary·AI 응답은 모의 응답이다.

WebKit 브라우저 회귀는 320·393·430·1280px 화면에서 편집·저장·재열기, 채널 변경 중 입력 보존, 브라우저 뒤로가기, 캡션 보존, 게시 제어와 버튼 hit test를 실행하고 화면을 남긴다. API는 격리된 합성 데이터다. 실제 iPhone의 가상 키보드·앱 전환과 실제 외부 게시 성공은 이 자동화만으로 검증됐다고 간주하지 않는다.

실제 인스타그램 게시, 운영 콘텐츠 삭제, 유료 AI 대량 호출은 검증에 사용하지 않는다. 공급자 계정의 실제 권한·한도·게시 성공은 별도의 제한된 운영 검증이 필요하다.

## 7. 롤백 기준

저장 후 재열기 불일치, 최신 원고와 다른 승인 사용, 미확정 자동 재전송, 같은 목적지 중복 게시 호출, 취소 확정 뒤 미시작 작업의 dispatch, health의 DB 실패가 확인되면 게시를 정지하고 수정 또는 앱 롤백을 검토한다.

이번 스키마는 추가 방식이므로 앱 롤백 때 컬럼·시도 기록을 삭제하지 않는다. 이전 앱은 새 phase·lease·계정 스냅샷 안전 규칙을 모르므로 **게시를 멈추지 않은 채 구버전으로 되돌리지 않는다**. 전송 중·unknown·새로 생성된 대기 승인 목록을 확인한 뒤 앱 버전을 되돌리고, 복구 완료 전 자동 게시를 재개하지 않는다.

## 8. 운영 제약

무료 Render 웹 인스턴스의 휴면·재시작 동안 정확한 예약 시각을 보장하지 않는다. 지연 건수와 실제 마지막 워커 동작을 표시하고, 깨어난 뒤 DB 대기 작업을 처리한다. 분 단위 정시 발행이 업무상 필수라면 같은 PostgreSQL 상태 모델을 사용하는 상시 실행 워커로 이동할 수 있다. Redis 도입은 그 전제조건이 아니다.

기사 접근 제한·유료 구독·봇 검증은 우회하지 않는다. 제목이나 다른 기사 본문을 원문으로 대체하지 않는다. 원문 직접 확인·본문 붙여넣기가 남는 복구 경로다.
